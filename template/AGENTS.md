# Agent Operating Rules — Mule 4 workspace

Always-on core. Keep it short; details live in skills (`.github/skills/*`) and path-scoped instructions (`.github/instructions/*`), loaded only when relevant.

## 0. Precedence (highest first)
1. The user's current message.
2. `.github/mule-starter/rulesets/<project>.md` — conventions of the project being changed.
3. `.github/instructions/house-style*.instructions.md` — workspace style generated by `/mule-init` from human-written code.
4. Shipped defaults (`.github/instructions/mule-*.instructions.md`, skills).
5. General knowledge.

Formatting tie-breaker: the file being edited wins. New code must be indistinguishable from the code around it (indentation, attribute layout, naming, quoting, blank lines, comment density, text language and tone).

## 1. Response mode
- Chat replies: `caveman` skill, level `full`, on by default. `normal mode` / `stop caveman` turns it off; `/caveman lite|full|ultra` switches level.
- Caveman never touches artifacts: code, comments, commit messages, PR text, docs, ruleset files follow house style in full sentences.
- Write normally for security warnings, destructive or irreversible actions, secrets, multi-step instructions the user must execute, and when the user is confused.
- Reply in the user's language. Artifacts use the workspace language from house style.

## 2. Token budget
- Read the smallest thing that answers the question: `grep -n` / outline first, then read a line range. Read a file whole only when the edit needs the whole file.
- Never read `.github/mule-starter/log.md` whole: `grep` the project name, take the last matches.
- Do not re-read a file you just wrote. Do not paste file contents back to the user; cite `path:line`.
- Each Maven run costs ~45 s before tests start: validate edits statically (`xmllint --noout`, YAML parse, DWL simulation), run the full project suite once after the last edit.

## 3. Work mode
1. **Analyze** — ruleset, target files, `memory/lessons.md` topic that matches. Never write code from a requirement alone; read the existing code first.
2. **Plan** — files to change and why; assumptions and risks in one line each.
3. **Implement** — minimum viable change, one task or one bug per run, only inside the target project.
4. **Test** — `mule-munit` skill: Test Necessity Gate first; write only tests that earn their place.
5. **Verify** — `verify-before-done` skill. No claim without a command run in this session.
6. **Review** — `mule-quality-gate` skill (or the `mule-reviewer` agent for independent review).

Default entry point for real work: the `mule-conductor` agent. Single-question answers need no pipeline.

## 4. Autonomy ladder (before asking the user anything)
1. Re-read local truth: ruleset, OAS, requirement text, recent log lines.
2. Read official docs (MuleSoft, HashiCorp, OWASP, vendor) for syntax/behavior questions.
3. Re-run the relevant scanner/validator to confirm the hypothesis.
4. One more self-heal pass.

Ask only for: a business rule the requirement does not state, a secret/credential, a missing task ID for a requested branch/commit, a platform mutation, `terraform apply`/`destroy`/state surgery, the 3-iteration cap being hit, or any action this session cannot undo.

## 5. Hard rules
- Scope: change only the target project; build exactly what was asked (`mvp-scope` rules in `mule-quality-gate`). Over-building is a defect.
- Comments: add none (no TODO/FIXME, no explanations) unless house style shows the workspace comments that kind of file; rationale goes in the reply or the log.
- No AI attribution anywhere: no `Co-Authored-By`/`Generated-by` trailers, no AI mentions in commits, branches, PRs, code or docs.
- Git: never `push`, `reset`, `clean`, `rebase`, or file-discarding `checkout`. Branch/commit only when the user asks, via `git-task-branch`, with a real task ID.
- Secrets: never write, echo, log or store credentials, tokens, decrypted values, PII. Encrypted placeholders stay placeholders; missing values are escalated, never invented.
- Tests: never delete, disable or weaken an existing test, never edit a passing test's expectations to fit new code.
- Fix loop: 3 failed iterations on one issue → stop and escalate with evidence.
- XML: no auto-formatting; match the surrounding layout byte-for-byte in style.
- No external upload of client code or data (pastebins, web tools).

## 6. State files (`.github/mule-starter/`)
| File | Purpose | Budget |
|---|---|---|
| `profile.md` | workspace facts from `/mule-init` (layers, build/test commands, env names, reference projects) | ≤ 6 KB |
| `rulesets/<project>.md` | per-project conventions (`mule-ruleset` skill) | ≤ 15 KB each |
| `memory/lessons.md` | durable, reusable gotchas only; one line each, newest first | ≤ 8 KB |
| `log.md` | one line per change: `- YYYY-MM-DD <project>: <file> — <what> (<task>)` | rotate at 300 lines |

Write a lesson only for a fact that would have prevented a real mistake and holds beyond this task. Task history goes to `log.md`, never to lessons.

## 7. Change summary
When more than one file changed: one table per project — `### <project>` then `File | Change` (path, one-line what/why; for XML add flow and `doc:name`).

## 8. Init contract
When asked to `/init`, "initialize", or regenerate instructions: run the `mule-init` skill end to end, then update `.github/copilot-instructions.md` without touching the `mule-starter` block.
